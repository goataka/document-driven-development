# モノレポ構成 - 概要

このドキュメントは、モノレポ（Monorepo）構成の概要と採用理由を説明します。

## モノレポとは

モノレポは、複数のプロジェクト（アプリケーション、ライブラリ、パッケージ）を単一のリポジトリで管理する開発手法です。

### モノレポ vs マルチレポ

| 項目 | モノレポ | マルチレポ |
|------|----------|------------|
| リポジトリ数 | 1つ | 複数 |
| コード共有 | 容易 | 煩雑 |
| 依存関係管理 | 一元管理 | 分散管理 |
| バージョニング | 統一可能 | 個別管理 |
| CI/CD設定 | 集約 | 分散 |
| 変更の影響範囲 | 把握しやすい | 把握しづらい |

## 採用理由

### 1. コードの再利用性向上

共通のコンポーネントやユーティリティを複数のアプリで使用：

```
packages/
├── ui-components/     # 共通UIコンポーネント
├── business-logic/    # ビジネスロジック
└── utils/             # ユーティリティ関数
```

### 2. 一貫性の確保

- すべてのプロジェクトで同じツール・設定を使用
- コーディング規約の統一
- 依存関係のバージョン統一

### 3. 開発効率の向上

- 1回のPRで関連する複数のプロジェクトを変更可能
- コードレビューが効率的
- リファクタリングが容易

### 4. 依存関係の明確化

- プロジェクト間の依存関係が可視化される
- 循環依存を検出しやすい

### 5. CI/CDの最適化

- 変更されたパッケージのみをビルド・テスト
- デプロイの自動化が容易

## 本プロジェクトでのモノレポ構成

### 対象プロジェクト

```
spec-driven-development/
├── docs/                   # ドキュメント
├── apps/                   # アプリケーション
│   ├── frontend/           # フロントエンドアプリ
│   ├── backend/            # バックエンドAPI
│   └── mobile/             # モバイルアプリ（将来）
├── packages/               # 共有パッケージ
│   ├── ui/                 # UIコンポーネント
│   ├── types/              # 型定義
│   ├── utils/              # ユーティリティ
│   └── config/             # 共通設定
├── sites/                  # website
│   ├── user-docs/          # ユーザーマニュアル
│   └── release-notes/      # リリースノート
└── tools/                  # 開発ツール・スクリプト
    ├── scripts/            # ビルド・デプロイスクリプト
    └── generators/         # コード生成ツール
```

### モノレポツール

以下のツールから選択：

#### 1. Turborepo（推奨）

**特徴**:
- 高速なビルドキャッシュ
- 並列実行の最適化
- シンプルな設定

**設定例**:
```json
// turbo.json
{
  "pipeline": {
    "build": {
      "dependsOn": ["^build"],
      "outputs": ["dist/**", ".next/**"]
    },
    "test": {
      "dependsOn": ["build"],
      "outputs": []
    },
    "lint": {
      "outputs": []
    },
    "dev": {
      "cache": false
    }
  }
}
```

#### 2. Nx

**特徴**:
- 依存関係グラフの可視化
- 影響範囲の分析
- プラグインエコシステム

#### 3. Lerna + Yarn Workspaces

**特徴**:
- 成熟したツール
- 柔軟な設定
- npmパッケージの公開に適している

## メリット

### 開発者視点

1. **コードナビゲーションが容易**: IDEで全体を検索・参照
2. **リファクタリングが安全**: 変更の影響をすぐに確認
3. **セットアップが簡単**: 1回のクローンとインストールで完了

### チーム視点

1. **コラボレーション向上**: すべてのコードが1箇所に
2. **知識共有**: チーム全体でコードベースを把握
3. **レビュー効率化**: 関連する変更をまとめてレビュー

### 運用視点

1. **デプロイの簡素化**: 統一されたCI/CDパイプライン
2. **バージョン管理**: 統一的なリリース管理
3. **セキュリティ**: 依存関係の一元的な更新

## デメリットと対策

### デメリット1: リポジトリサイズの増大

**対策**:
- Git LFS（Large File Storage）の使用
- 不要なファイルの除外（.gitignore）
- 定期的なクリーンアップ

### デメリット2: ビルド時間の増加

**対策**:
- 増分ビルドの活用（Turborepo）
- 変更されたパッケージのみビルド
- ビルドキャッシュの利用

### デメリット3: アクセス制御の複雑化

**対策**:
- サブディレクトリごとのCODEOWNERS設定
- ブランチ保護ルール
- PRレビュー必須化

### デメリット4: 学習コスト

**対策**:
- 充実したドキュメント
- セットアップガイド
- チーム内勉強会

## 適用シナリオ

### モノレポが適している場合

- フロントエンドとバックエンドを同時開発
- 複数のアプリで共通コードを使用
- 頻繁にプロジェクト間で変更が発生
- チーム全体でコードベースを把握したい

### マルチレポが適している場合

- プロジェクト間の独立性が高い
- デプロイサイクルが異なる
- アクセス制御を厳格に分ける必要がある
- 異なる技術スタックを使用
