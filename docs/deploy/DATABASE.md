# データベース管理方針

本ドキュメントは、データベースの管理方針とDynamoDB運用戦略を説明します。

---

## データベース戦略

### 基本方針

**DynamoDBの採用**:
- コスト最適化: オンデマンド課金で使用量に応じた支払い
- 完全マネージド: サーバー管理不要、自動スケーリング
- 高可用性: マルチAZ自動レプリケーション
- 高速性能: 一桁ミリ秒のレイテンシ保証
- NoSQL柔軟性: スキーマレスなデータモデル

---

## 環境別データベース構成

### 1. ローカル環境
**方針**:
- LocalStackでDynamoDBをエミュレート
- ローカル開発に完全対応
- コストゼロ

**構成**:
- LocalStack DynamoDB
- 開発用シードデータ自動投入
- テーブル定義の自動作成
- AWS SDK互換APIで動作確認

### 2. CI環境
**方針**:
- LocalStackで一時的なDynamoDB起動
- テスト完了後は自動削除
- 並列実行可能

**構成**:
- LocalStack DynamoDBコンテナ（テストごと）
- クリーンな状態から開始
- GitHub Actions無料枠内
- AWS SDK互換で実環境と同じコード

### 3. 検証環境（AWS）
**方針**:
- 最小構成で低コスト運用
- 開発チーム内テスト用
- オンデマンドモード使用

**構成**:
- DynamoDB（オンデマンド課金）
- ポイントインタイムリカバリ: 有効（最小限）
- 自動バックアップ: 1日保持

**コスト目安**: 月額 $3-8（低トラフィック想定）

### 4. ステージング環境（AWS）
**方針**:
- 本番同等構成
- 低コスト運用

**構成**:
- DynamoDB（オンデマンド課金）
- ポイントインタイムリカバリ: 有効
- 自動バックアップ: 3日保持
- グローバルテーブル: 無効（コスト削減）

**コスト目安**: 月額 $5-15

### 5. 本番環境（AWS）
**方針**:
- 高可用性とパフォーマンス
- 自動スケーリング

**構成**:
- DynamoDB（オンデマンド課金）
- ポイントインタイムリカバリ: 有効
- 自動バックアップ: 7日保持
- グローバルテーブル: 検討可能（多地域展開時）
- DynamoDB Streams: イベント駆動処理用

**コスト目安**: 月額 $15-60（トラフィック次第）

## データモデル設計戦略

### 方針
- Single Table Designの検討
- アクセスパターンベースの設計
- パーティションキーとソートキーの最適化

### プロセス
1. ローカルでテーブル設計・テスト（LocalStack）
2. CIでデータモデル検証
3. ステージング環境で実行
4. 本番環境で実行（承認後）

### ツール
- AWS SDK for JavaScript
- DynamoDB Toolboxの検討
- インフラストラクチャ as Code（CDK/Terraform）

---

## バックアップ戦略

### 自動バックアップ
- DynamoDB の継続的バックアップ（PITR）
- 環境別に保持期間設定
- ポイントインタイムリカバリ（35日間）

### 手動バックアップ
- リリース前にオンデマンドバックアップ
- 重要な変更前にバックアップ
- スナップショット保持: 30日

### バックアップ検証
- 定期的にリストアテスト
- ステージング環境でリストア確認
- RTO/RPO目標の確認

---

## 接続管理方針

### Lambda からの接続
**特性**: DynamoDBはHTTP APIベースで接続管理不要

**対策方針**:
- AWS SDK v3の使用
- 接続プールは不要（HTTPベース）
- リトライロジックの設定
- タイムアウトの適切な設定

### リクエスト管理
- 環境別にスロットリング設定
- 監視とアラート設定
- オンデマンドモードで自動スケーリング

---

## セキュリティ方針

### アクセス制御
- IAM ロールベースのアクセス制御
- 最小権限の原則
- VPCエンドポイント経由のアクセス（オプション）

### データ暗号化
- 保存データ暗号化（デフォルト有効、AWS KMS）
- 転送データ暗号化（HTTPS必須）
- シークレット管理: AWS Secrets Manager

### 監査
- CloudTrail でAPI呼び出し記録
- CloudWatch Logsでアクセスログ
- 定期的なアクセスパターン確認

---

## パフォーマンス最適化方針

### インデックス戦略
- グローバルセカンダリインデックス（GSI）の活用
- ローカルセカンダリインデックス（LSI）の検討
- スパースインデックスの利用

### クエリ最適化
- バッチ操作の活用（BatchGetItem, BatchWriteItem）
- クエリ vs スキャンの適切な選択
- ページネーション実装

### キャッシュ戦略
- DAX（DynamoDB Accelerator）の検討（高頻度読み取り）
- アプリケーションレベルキャッシュ
- CloudFrontでのAPIキャッシュ（適宜）

---

## コスト最適化

### 課金モードの最適化
- オンデマンドモード: トラフィック予測困難な場合
- プロビジョニングモード: 安定したトラフィックの場合
- 定期的な利用状況確認と調整

### 不要なリソースの削減
- 未使用GSIの削除
- 古いバックアップの削除
- 不要なデータのアーカイブ（S3へ移行）
